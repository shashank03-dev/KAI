# Live Gemma 4 runs: the harness fixes and every switch, measured

Date: 2026-10-12. Model: `gemma-4-26b-a4b-it` on the Gemini API (free tier,
two keys used in turn). Raw files: [`2026-10-12-live/`](2026-10-12-live/),
kept in a subfolder so `kai bench report` does not merge them into the
head-to-head table.

## How it was measured

- **Machine:** this repo's Linux container (4 vCPU, Ubuntu 24.04), Xvfb
  `:99` at 1920x1080 with openbox and the AT-SPI bus
  (`scripts/desktop/start.sh`), Firefox ESR 140, Mousepad, pcmanfm.
- **Tasks:** the same 14 as the 2026-10-10 head-to-head (web search, form
  fill, web form submit, download, rename, largest file, zip, open folder,
  write in Mousepad, close an app, tip calculator, calendar event, image
  resize, screenshot). A task passes only if its `check` command passes.
- **Command:** `kai bench --backend gemini --model gemma-4-26b-a4b-it --yes
  --no-record --only …` plus the switch under test. Every configuration ran
  **twice**, interleaved (old, new, then each switch, then the second
  round), so time-of-day effects hit every side alike.
- **"old"** is the build at the start of this session (`389b576`);
  **"new"** is after the live-run fixes below (`6a8eb7f`). Every switch was
  measured on "new". Before measuring, the bench desktop itself was fixed
  (Firefox could not load any page through the proxy, and leftover dialogs
  covered later tasks; see `c2a8b50`); all runs below use the fixed desktop.
- **Rate limits:** the free tier's binding limit was
  `GenerateContentInputTokensPerModelPerMinute-FreeTier` (now named in Kai's
  log). Waits are not model time; wall time includes them and varied with
  load, so it is listed but not compared.

## What the numbers say

- **The harness fixes are the real gain.** Against the old harness, the new
  one used 25% fewer steps, 34% fewer model calls and 36% fewer input tokens
  over the same 28 task runs, with 27/28 against 28/28 passed (the one miss
  is a false done, below). They are fixes, not switches, so they ship.
- **No switch earns a default.** The rule was: on only where the pass rate
  holds and the target metric improves.
  - `--outcomes` (target: false done): false done did not go to zero (1 vs
    1), steps rose 69% and calls 66% (36 gate refusals). Off.
  - `--macro-history` (target: steps, calls): both went up. Off.
  - `--recover` (target: stalls): 28/28, but 22% more calls than "new". Off.
  - window scope (target: tokens, privacy): 28/28, tokens per call
    unchanged (the API seems to bill an image at a fixed size whatever its
    pixels), steps +6%. Off; worth it as a privacy option, not for cost.
  - `--best-of 3` (target: long tasks): 25/28 and 67% more calls on these
    short tasks. Off.
  - procedures: replays happen (checked in replay mode: two successes, then
    the third run replays), but on these tasks the live gain is small and one
    run per side cannot separate it from noise. Off.
- **False done remains Gemma's main failure here:** `open-folder`, where it
  lists the folder in the terminal instead of opening the file manager. The
  DONE gate did not stop it (the model named no outcome a probe could
  check).
- **Visual re-aim for procedures (item 5) is not built:** no replay was seen
  failing on a renamed target, which was the condition for building it.

Two runs per side on 14 tasks is still small: a 1–2 task difference is not
significant. The step and call reductions of the new harness are large and
consistent across both runs (89 and 91 steps vs 96 and 144).

## Fixed because of these runs

Seen in the live runs and fixed before (or between) the measured runs:
empty `shell` replies with the command in a follow-up, a silent shell step
reported as "the screen has not changed" (Gemma then threw working commands
away), the same command repeated up to 40 times, `open_url` without a URL,
429 retries ignoring `RetryInfo`, Gemma killing Kai's own process from a
`ps | grep` match, and `xdg-open` blocking for 180 s. Details in
`DECISIONS.md` (2026-10-12, live runs).
