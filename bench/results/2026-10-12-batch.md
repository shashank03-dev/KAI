# Feature batch (2026-10-12): no regression with every new switch on

The batch adds macro-action history, procedures, screen-scoped lessons and
app facts, best-of-N plans, memory consolidation and the exam, `kai mcp`,
and diagnosed recovery. Every runtime switch is **off by default**. None was
measured on a live model: this container has no model key and no browser
or GUI apps (see [2026-10-12-verification.md](2026-10-12-verification.md)).
So this page answers one question only: **does turning everything on
break or slow anything when no model is involved?**

Same container, final build, `--no-record`:

| Run | Pass | Steps per task | Model calls | Step p50 / p95 ms |
|---|---|---|---|---|
| mock (30 tasks), all off | 30 / 30 | — | — | 0 / 0 |
| mock, `--outcomes --macro-history --procedures --best-of 3 --recover` | 30 / 30 | — | — | 0 / 0 |
| replay under Xvfb (20 terminal/mixed tasks), all off | 19 / 20 | 2.40 | 47 | 112 / 481 |
| replay, all on (as above) | 19 / 20 | 2.40 | 47 | 105 / 204 |

- The one replay failure is the same in both runs and in every run on
  2026-10-12: `dark-mode`, `env_error` (its setup needs a GNOME schema
  this container lacks).
- The bench ignores `--best-of` for mock and replay (recorded replies hold
  no plans) and says so. Procedures need two successful runs before they
  replay, so a single bench pass never replays one.
- The p95 gap is noise between runs, not a difference the switches make.
  The mechanisms are proven by tests, not by these numbers: 449 workspace
  tests, fmt and clippy `-D warnings` clean, skills 10/10.

Raw files: [`2026-10-12-batch/`](2026-10-12-batch/). To measure the gains,
use a live backend with the A/B commands in each feature's doc
(VERIFICATION.md, PROCEDURES.md, MEMORY.md, HARNESS.md).
