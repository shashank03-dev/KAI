# Rebuild Kai's eyes, keep its brain

As of October 2026, the strongest stack for an open-source, open-weight desktop agent that targets macOS (Apple Silicon) first and Linux second is the shape Kai already has. It is a Rust harness that is free of OS code, perception that reads the accessibility tree first and adds a screenshot, a llama.cpp sidecar that speaks the OpenAI API, a CDP browser lane, and one internal action schema with an adapter for each model. **Kai does not need a new language or a new UI framework. It needs a new OS layer on the Mac.** The macOS weak points are capture, signing and permissions. Kai captures through `CGWindowListCreateImage`, which the macOS 15 SDK has obsoleted. Its ad hoc signature loses the permission grants on every rebuild. And no live model has ever run a task on a Mac. These matter more than any choice of model or UI. On Linux the deciding gap is Wayland input, which needs the RemoteDesktop portal with libei. The controlled evidence on perception, though it comes from 2025 and early 2026, favours an accessibility tree plus a screenshot for a general model like Gemma 4. Coordinates from the screenshot alone pay off only with a model trained on GUI grounding. That makes "Gemma plans, a small Qwen3-VL-derived grounder points, used only when needed" the experiment worth running. A wholesale switch to Holo4 is not. The 2026 OSWorld-Verified scores in the 80s (Qwen3.8 Max, Holo4, Kimi K3, Claude Fable 5) come from aggregators or vendor posts that this research could not check against the official leaderboard. They should not drive any decision until they are reproduced. Recommended next step: move macOS capture to ScreenCaptureKit, sign with a stable certificate, and then run a paired `kai bench` A/B on a Retina Mac. The A/B compares Gemma alone with Gemma plus a grounder that is called only when needed.

*Evidence tags used throughout: **[P]** primary (official docs, papers, model cards, crates.io, measurements in Kai's repo); **[V]** reported by a vendor, or a vendor figure relayed by a secondary source; **[A]** an aggregator leaderboard, not verified; **[I]** this report's inference.*

The aggregators also disagree with one another. BenchLM lists a "Holo3-35B-A3B" at 82.6%. Secondary coverage of H Company's late-September release says the 35B-A3B model is **Holo4**, at 80.8%. Simular, for its part, says Google has made no OSWorld-Verified submission at all ([Simular](https://www.simular.ai/alternatives/gemini-computer-use-alternatives)). Two things follow [I]. First, **open-weight models that run on a laptop are proven on primary sources at roughly 37–45% OSWorld-Verified, not 80%.** Second, the most robust primary finding is about training, not size: Holo2-4B (37.7%) matches Qwen3-VL-30B-A3B-Thinking (36.6%), while an untrained Qwen2.5-VL-72B scores 5% ([Holo2 card](https://huggingface.co/Hcompany/Holo2-30B-A3B); [OpenCUA card](https://huggingface.co/xlangai/OpenCUA-32B)).

Kai's own evidence is just as narrow, and its docs say so. Every live-model number comes from a Linux Xvfb container with 4 vCPU and no GPU, mostly Gemma 4 26B-A4B through the Gemini API, one or two runs per side, on Kai's own 14–30 tasks. The repo's architecture review states that "there is no defensible percentage improvement in accuracy or speed yet" ([ARCHITECTURE_REVIEW](reviews/ARCHITECTURE_REVIEW_2026_10_17.md); [README](../README.md)) [P]. The macOS acceptance checklist is "prepared, not executed" ([MAC_GUI_TESTING](../docs/MAC_GUI_TESTING.md)). In short, every Mac decision below starts from an unvalidated port of a harness built for Linux first.

## Accessibility-plus-screenshot beats pixels for a general model

The controlled ablations favour Kai's existing design. In OS-Harm's comparison of OSWorld observation types, **Gemini 2.5 Pro scored 25.6% with a11y tree plus screenshot, 21.1% with the tree alone, and 5.3% with the screenshot alone**. For o4-mini, Set-of-Marks (18.9%) and the hybrid (18.4%) were the two best observation types ([OS-Harm](https://arxiv.org/pdf/2506.14866)) [P]. EntWorld (January 2026) also found the combination strongest and screenshot-only weakest on enterprise apps. It warned that tree-only fails where accessibility metadata is incomplete and that trees cost tokens ([EntWorld](https://arxiv.org/pdf/2601.17722)) [P]. RedTeamCUA found that adding the tree **lowered prompt-injection success** ([RedTeamCUA](https://arxiv.org/pdf/2505.21936)) [P], which fits Kai's guarantee that page text is treated as data. The counterweight is OSWorld-Human: the tree **raised step counts for most apps**, sharply in LibreOffice, although it lowered them in GIMP and Chrome ([OSWorld-Human](https://arxiv.org/pdf/2506.16042)) [P]. So the tree should be filtered to interactive elements in the viewport, not dumped whole [I]. The products that ship this way agree. Codex's macOS computer use (April 2026) reads the AX tree and runs in the background with its own cursor ([mjtsai](https://mjtsai.com/blog/2026/04/17/)) [V]. UFO² mixes UIA with visual signals and batches actions speculatively, which **cut LLM calls by 51%** ([UFO](https://github.com/microsoft/UFO)) [P].

The top OSWorld systems still look at screenshots only, but they pair the screenshot with a model trained on GUI grounding. OpenCUA's leading run uses `--observation_type screenshot` with three images of history ([OpenCUA card](https://huggingface.co/xlangai/OpenCUA-32B)) [P]. Agent S3 splits a frontier planner from a UI-TARS-1.5-7B grounder ([Agent-S](https://github.com/simular-ai/Agent-S)) [P]. The grounders worth considering in October 2026 are all Qwen3-VL derivatives. **MAI-UI reaches 73.5% on ScreenSpot-Pro with zoom-in** ([MAI-UI](https://arxiv.org/abs/2512.22047)), **UI-Venus-1.5 reaches 69.6%** ([UI-Venus-1.5](https://arxiv.org/abs/2602.09082)), and **Holo2-4B scores 57.2% at only 4B** ([Holo2 card](https://huggingface.co/Hcompany/Holo2-30B-A3B)) [P]. UI-TARS-1.5-7B, which Agent S still recommends, scores only 39.0% on the same table. ScreenSpot-v2 is saturated, with almost everything at 91–95%, so only ScreenSpot-Pro, OSWorld-G and UI-Vision tell grounders apart [I]. Zoom matters too: Ferret-UI Lite reaches 53.3% ScreenSpot-Pro at 3B with crop-and-zoom ([Apple ML Research](https://machinelearning.apple.com/research/ferret-ui)) [P], and Anthropic ships a `zoom` action in `computer_toolset_20260801` ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)) [P].

Gemma 4, Kai's default, is the unknown in all of this. It returns `box_2d` JSON relative to a 1000×1000 frame and offers image budgets of 70 to 1120 tokens, but **no ScreenSpot or OSWorld score for Gemma 4 exists anywhere** ([HF Gemma 4 blog](https://huggingface.co/blog/gemma4)) [P]. Kai's only head-to-head (Gemma 26B-A4B 14/14 at 2.85 s p50 against GPT-5 mini 12/14, one run each) used its own Linux tasks with Set-of-Marks, not pixel grounding ([README](../README.md)) [P]. The conclusion [I] is to **keep hybrid marks with Gemma as the default** and to treat a specialised grounder as an *escalation*. It should be called when the tree is missing (Qt 5 publishes no AT-SPI tree, per [DRIVER_MATRIX](../docs/DRIVER_MATRIX.md)) or when a target is ambiguous. It should not be called on every step: each call adds one model round trip, and single-model GUI agents are the latency-efficient choice. Behaviour Best-of-N, the largest single published gain (66% → 72.6%), needs several isolated rollouts with a judge. It suits benchmarks and VMs, not a user's live desktop, so it is rejected for the app.

## llama.cpp stays; MLX earns at most a Mac-only switch

A computer-use step is heavy on prefill: about 1–2.5K image tokens plus history in, a short action out. So time-to-first-token matters more than decode speed [I]. On that measure, the only dated vision head-to-head found shows **near parity on Apple Silicon**. On an M4 Max with Qwen3-VL-2B 4-bit, mlx-vlm and llama.cpp decoded at 217–239 tok/s. mlx-vlm was 7–17% faster to first output at small image sizes, and the 448×896 gap was under 8% ([RunAnywhere, 2026-03-13](https://www.runanywhere.ai/blog/metalrt-vlm-fastest-vision-language-model-apple-silicon)) [V]. MLX's larger leads apply to MoE text models (roughly 1.4–1.8x), and Apple reports M5 Neural Accelerators giving a **4.06x faster TTFT** than M4 under MLX on a text model ([yage.ai](https://yage.ai/share/mlx-apple-silicon-en-20260331.html)) [V]. Against that, llama.cpp `llama-server` (Kai pins b11429) is the only option that is a single prebuilt, hash-pinnable binary on every OS with no Python. It already offers vision through `--mmproj`, `json_schema` and GBNF constraints, `--jinja` tool calling, prompt caching, slot save/restore, `/v1/responses` and Anthropic `/v1/messages` ([llama-server README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md)) [P]. Ollama is not an alternative: in one report, raw llama.cpp Metal ran at **89.4 tok/s against 43.5 tok/s through Ollama** on the same M4 Max ([yage.ai](https://yage.ai/share/mlx-apple-silicon-en-20260331.html)) [V]. The verdict [I] is to keep llama.cpp as the shipped runtime. vllm-mlx is the right shape for an MLX switch on macOS only, off by default and worth testing first on M5 machines: it is OpenAI- and Anthropic-compatible, has JSON-schema output, 19 tool-call parsers and an image prefix cache ([vllm-mlx](https://github.com/waybarrios/vllm-mlx)). Because it speaks the same API, Kai's `OpenAiClient` would need no changes.

Quantization is a blind spot nobody has measured for GUI grounding. The nearest evidence shows 4-bit VLM quantization costing only about 1% of aggregate score while **flipping 19–21% of individual predictions** ([arXiv 2503.06794](https://arxiv.org/pdf/2503.06794)) [P]. Kai should keep the mmproj at F16 or BF16 and prefer Q5_K_M or Q8_0 weights for any grounder until its own bench shows Q4 holds [I].

On protocols, the four vendor schemas share the same primitives but differ in syntax and coordinate frame. OpenAI returns a batched `actions[]` in pixels ([OpenAI](https://developers.openai.com/api/docs/guides/tools-computer-use)). Anthropic has a 17-member toolset in screenshot pixels ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)). Gemini uses a 0–999 grid with `intent` strings ([Gemini docs](https://ai.google.dev/gemini-api/docs/computer-use)). Fara-7B uses pixels at 1428×896 ([Fara-7B card](https://huggingface.co/microsoft/Fara-7B)). The open-model formats differ as well. OpenCUA emits absolute pixels on a smart-resized image ([OpenCUA card](https://huggingface.co/xlangai/OpenCUA-32B)). UI-TARS emits text `Thought/Action` strings ([UI-TARS](https://cdn.jsdelivr.net/gh/bytedance/UI-TARS@main/README_v1.md)). Qwen3-VL derivatives emit 0–1000 relative coordinates, and sources disagree on whether the divisor is 999 or 1000 ([CutVerse](https://arxiv.org/pdf/2605.19484)) [P]. Kai's `--oai-contract` frames (`marks`, `pixels`, `norm1000`, `smart-resize`) and its versioned action vocabulary are therefore the right integration point ([COMPUTER_TOOLS](../docs/COMPUTER_TOOLS.md)). Today they are only fixture-tested, and the repo's own scorecard warns that "catalog entries do not imply correct model-native chat templates or action parsers" ([SCORECARD](reviews/OPEN_MODEL_COMPUTER_USE_SCORECARD_2026_10_16.md)) [P]. The rule [I] is to constrain generic models (Gemma, plain Qwen) with a grammar and to parse fine-tuned models in their native format. MCP is not a model protocol; it is for exposing Kai's hands to other agents, which `kai mcp` already does.

## macOS capture and signing, not models, block a Mac-first launch

**Capture is on borrowed time.** xcap 0.9.8 captures on macOS with `CGWindowListCreateImage` ([crates.io xcap](https://crates.io/api/v1/crates/xcap)) [P]. That API, along with `CGDisplayCreateImage`, is unavailable when building against the macOS 15 SDK ([eclipsa #10](https://github.com/google/eclipsa-audio-plugin/issues/10); [MacPorts #70756](https://trac.macports.org/ticket/70756)) [P]. Kai's macOS-15 runner still passed at runtime ([MACOS.md](../docs/MACOS.md)), but the next SDK bump breaks the build, and MACOS.md rejected ScreenCaptureKit before anyone assessed this risk. ScreenCaptureKit is the only forward path, and it comes with a cost no agent can avoid. Apple DTS reproduced a **"bypass the system private window picker… Allow for one month" alert** for any non-picker capture, `SCScreenshotManager` included. The only exemptions are an entitlement reserved for screen-sharing products and the `SCContentSharingPicker` ([Apple Forums 765103](https://developer.apple.com/forums/thread/765103)) [P]. The picker cannot serve unattended screenshots either: `SCScreenshotManager` on a picker filter fails with -3801, and a pick does not survive a relaunch ([openscreen PR #737](https://github.com/getopenscreen/openscreen/pull/737)) [P]. So Kai must accept the monthly re-consent and detect it by treating -3801 as revoked [I]. It should also use a long-lived `SCStream` with an `SCContentFilter` that excludes its own windows. That replaces the current approach of painting over its own windows, because `sharingType = none` is not reliably honoured by modern capture ([Apple Forums 808016](https://developer.apple.com/forums/thread/808016)) [P]. Tahoe makes the bundle matter more. In macOS 26.1, unbundled executables stopped appearing in the Screen Recording pane ([Apple Forums 807323](https://developer.apple.com/forums/thread/807323)), and child processes may not inherit the grant ([openclaw#14138](https://github.com/openclaw/openclaw/issues/14138)) [P]. For Rust, the `screencapturekit` crate is actively versioned up to 8.x ([docs.rs](https://docs.rs/screencapturekit)) [P]. The generated `objc2-screen-capture-kit` would match Kai's existing objc2 0.3 crates, but that is background knowledge to check before adopting it [I].

**Signing is a correctness bug, not a polish item.** With ad hoc signing, macOS pins the Accessibility grant to the cdhash, so every rebuild silently revokes it while the switch in System Settings still shows "on". A real certificate kept the grant through six rebuild-and-reinstall cycles ([shannoncoat](https://git.bdeshi.space/bdeshi/shannoncoat/src/tag/0.0.8)) [P, practitioner]. Kai's MACOS.md documents exactly this symptom. A stable self-signed or Apple Development certificate fixes permissions for development. Developer ID plus notarization is needed only for Gatekeeper on downloads. Cua's driver shows the pattern to copy: one signed app identity launched through LaunchServices, a `status` check that never prompts, a `grant` flow that requires a live capture probe, and a relaunch after the grant ([Cua docs](https://cua.ai/docs/reference/cua-driver/macos-permissions)) [P]. That also closes Kai's audit item A13, where permission badges turn green without the capability ever being exercised. The App Sandbox rules out the Mac App Store for any app that controls others [I, background knowledge].

The rest of Kai's Mac OS layer is sound and should stay. The AX reader uses one `AXUIElementCopyMultipleAttributeValues` per element, a 0.25 s messaging timeout and `AXManualAccessibility` for Electron, which matches Electron's documented switch ([Electron a11y docs](https://docs.w3cub.com/electron/tutorial/accessibility)) [P]. It read the TextEdit tree in 10 ms ([MACOS.md](../docs/MACOS.md)). Input goes through `CGEventPost` via enigo, with Retina points mapped from capture pixels. Background operation with its own cursor, which Codex ships, is a later step, built on window-scoped ScreenCaptureKit capture plus AX actions that need no pointer [I].

**Linux needs portals for Wayland, not another crate swap.** X11 with XTest and AT-SPI2 works without consent dialogs. On Wayland the only sanctioned path is the ScreenCast portal over PipeWire, plus the RemoteDesktop portal's `ConnectToEIS` with libei for input ([KDE 6.1](https://www.phoronix.com/news/KDE-Plasma-6.1-Beta); [libei](https://libinput.pages.freedesktop.org/libei/api/)) [P]. Restore tokens that are supposed to skip repeat prompts were buggy on both desktops in 2026. KDE issued a token even when the user unchecked "restore" ([KDE 517454](https://bugs.kde.org/show_bug.cgi?id=517454)), Plasma 6.7.2 rejected tokens after a restart ([tigervnc-users](https://groups.google.com/g/tigervnc-users/c/cdv-YPjQvkU)), and GNOME re-prompts when sessions are created and destroyed repeatedly ([ConnectWise](https://screenconnect.product.connectwise.com/communities/1/topics/5169-bug-linux-client-repeatedly-opens-gnome-remote-desktop-permission-dialogs-and-ignores-restore-token)) [P]. Kai should therefore hold one long-lived portal session, store the token in the keychain, and fall back cleanly to a fresh dialog [I]. AT-SPI on Wayland cannot give global coordinates, and GTK 4.10+ reported (0,0) extents ([at-spi2-core#14](https://gitlab.gnome.org/GNOME/at-spi2-core/issues/14); [GTK#6343](https://gitlab.gnome.org/GNOME/gtk/-/issues/6343)) [P]. So on Wayland, Kai should prefer AT-SPI `Action` and `EditableText` and take click positions from the screenshot rather than from extents [I]. uinput/ydotool needs root or a udev rule and depends on the keyboard layout, so it should stay an explicit opt-in ([Debian ydotool](https://sources.debian.org/src/ydotool/1.0.4-3/README.md)) [P]. The Rust pieces (`ashpd`, `reis`, `pipewire-rs`) are background knowledge and their 2026 maintenance was not verified [I].

## GPUI stays, but Ely and the settings seam need insulation

No major computer-use agent uses GPUI. Electron dominates AI clients (Claude desktop, UI-TARS Desktop), ChatGPT for Mac is native Swift, and teams with a Rust engine pick Tauri: Screenpipe, Jan's rebuild, and Cua's Linux app ([Daring Fireball](https://daringfireball.net/2026/07/claudes_criminally_bad_mac_app_is_an_inside_job); [Screenpipe](https://docs.screenpi.pe/architecture); [Cua](https://github.com/trycua/cua)) [P/V]. Even so, the evidence does not justify a rewrite. kai-core (about 31k lines) and kai-os (about 13k) have no UI dependency, and the UI layer is about 14k lines. Of its 57 files, 43 touch GPUI or Ely, so a framework swap means a rewrite, not a port ([kai_audit, repo measurement](../crates/kai-app/src)) [P]. Each alternative buys a new problem. **Tauri** puts a WebKitGTK webview on Linux, and Tauri's own docs list blank windows, crashes and slow WebGL fallbacks on NVIDIA/DMABUF ([Tauri Linux graphics](https://v2.tauri.app/develop/debug/linux-graphics/)) [P]. It would also require a TypeScript UI plus an IPC schema over the engine. **Electron** needs a sidecar or N-API bridge and ships Chromium (Notion's Mac app is 518 MB per [Daring Fireball](https://daringfireball.net/2026/07/claudes_criminally_bad_mac_app_is_an_inside_job)) [V]. **SwiftUI** gives the best Mac fit but leaves Linux without a UI, so Kai would maintain two. Slint (stable 1.18.1) is the only plausible Rust-native fallback ([crates.io slint](https://crates.io/crates/slint)) [P].

The real UI risk is supply-chain, not the renderer. Kai pins `gpui-pre =0.3.8`, a weekly snapshot of Zed main published by a single owner. It is already one release behind 0.3.9, while the official `gpui` crate has not moved past 0.2.2 (2025-10-22) ([crates.io gpui-pre](https://crates.io/crates/gpui-pre); [crates.io gpui](https://crates.io/crates/gpui)) [P]. The component library, Ely, is about 250k vendored lines whose upstream stopped being cloneable. It has already caused the one recorded Mac crash, a `Select` assertion on zero choices, fixed in `bb46617` ([DECISIONS.md](../DECISIONS.md)) [P]. Meanwhile gpui-component, which powers Longbridge Pro, ships weekly and is at 0.7.3 ([crates.io gpui-component](https://crates.io/crates/gpui-component); [Zed blog](https://zed.dev/blog/community-champion-jason-lee)) [P]. The renderer is proven in Zed 1.0 on macOS and Linux. So the recommendation [I] is to keep GPUI, put a stable settings and run-event façade between kai-app and kai-core (`settings` alone has 41 call references, the tightest seam), and migrate screens off Ely onto gpui-component one at a time. That way the UI can upgrade, or be replaced by Slint, without touching the harness.

### Hypothesis and measurement

The bet [I] has two parts. **H1 (engineering):** moving Mac capture to a long-lived ScreenCaptureKit stream is latency-neutral or better than xcap. It also removes the own-window masking step without changing pass rates. **H2 (accuracy):** on a Retina Apple Silicon Mac, Gemma 4 26B-A4B with hybrid marks (local, llama.cpp Metal) beats a pixel-native grounder used alone on AX-rich apps, in steps and wall time at an equal or higher pass rate. And Gemma plus grounder escalation beats Gemma alone on AX-poor apps (Qt, canvas, Electron without the a11y switch), with median step latency rising by no more than one grounder call on the escalated steps only.

Measurement follows the repo rule of at least two live runs per side; three are recommended here, because Kai has seen 8/14 and 6/14 on identical configs ([local bench](../bench/results/2026-10-13-local.md)). Every run gets its own `--out` directory. Each side runs the same Mac task set at temperature 0, with task checks or the DONE gate on so that a pass is verified, not claimed (audit item A12). The record for each run includes chip, RAM, macOS version and display scale. Metrics are verified passes, false-done count, steps, model calls, input tokens, wall time, model p50, and the harness's own observe-phase p50/p95. A Gemini-API Gemma control separates model variance from local-runtime variance. A grounder sub-arm compares Q4_K_M with Q8_0 weights, with mmproj at F16. A side wins only if its margin exceeds the spread between its own two baseline runs. Each new behaviour ships off by default until it wins (CLAUDE.md).

### Rejected, and why

A **Tauri rewrite** was rejected for the WebKitGTK failures on Linux and because it means a TypeScript UI plus IPC over a working Rust engine. **Electron** was rejected for its size, the sidecar or N-API bridge, and a second language. **A SwiftUI app** was rejected because it leaves Linux with a second UI; a Swift helper is justified only if a Swift-only API becomes necessary, and it would need its own TCC identity. **A Python harness** was rejected because TCC attributes grants to "Python" or the terminal, and that broke Cua on Tahoe ([cua#870](https://github.com/trycua/cua/issues/870)). **Ollama** was rejected for its wrapper overhead and because it is a system service. **MLX as the default** was rejected because the gain over llama.cpp is small on M1–M4, and it means Python and macOS only. **Screenshot-only coordinates as the default for Gemma** were rejected on the OS-Harm numbers (5.3% against 25.6% hybrid). **bBoN or GTA1-style multi-rollout judging** was rejected because it needs parallel isolated environments. **The SCContentSharingPicker** was rejected because it cannot serve unattended screenshots. **uinput by default** was rejected because it needs root and depends on the keyboard layout. **Holo4 as the default model** was rejected for now: its scores are secondary only, Holo-family licences contradict each other (the Holo2 card says both CC BY-NC and Apache 2.0), and no Kai calibration exists.

## Conclusion

The research turns the question around. Choosing a stack for a Mac-first open-weight agent in 2026 is no longer mainly about the model or the UI toolkit. The published gains come from the harness: hybrid perception, specialised grounding used only when needed, batching and verification. The failures come from the operating system: obsoleted capture APIs, signature-bound permissions and Wayland's consent model. Kai's architecture already sits on the right side of that divide. Its risk is that it has never been measured on the platform it now calls first. The 80%-plus open-model leaderboard figures, even if they turn out to be real, belong to 27–35B systems on someone else's harness. The 37–45% primary-sourced range is the honest prior for what a laptop can do.

The deeper implication is that Kai's competitive edge, if it has one, is Linux-native and Mac-native accessibility control with an open model. Most consumer agents skip Linux entirely, and Codex validates the AX-tree approach on Mac. Making that edge real requires the unglamorous sequence: ScreenCaptureKit, a stable signature, a Mac task set, and paired runs. Only after those does it make sense to spend on grounders, MLX or new models.
