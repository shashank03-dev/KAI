# Phase 4: step candidates and disposable trajectory rollouts

Design note (2026-10-16). Source: [OpenAI parity research](RESEARCH_2026_10_OPENAI_PARITY.md) §5d and §7, plus the current Kai `ModelClient`, computer executor, trace and bench implementations. The underlying best-of-N observations in that research come from Agent S3 and GTA1; Kai has no live measured benefit yet.

## Implementation

`--oai-contract ... --step-candidates K` generates independent candidates at temperature 0.7 (K = 2–8). A vLLM client requests `n=K` choices in a **single non-streaming** structured-output request; all other backends make parallel individual requests. vLLM falls back to parallel calls only if its endpoint explicitly rejects multi-choice generation. Incomplete or malformed multi-choice responses fail rather than silently reducing K. Each valid reply is decoded into screen coordinates and assigned to a disjoint, pairwise-agreeing cluster by element or nearby screen point (12 px). Bounded subset search finds the largest agreeing cluster instead of relying on order-sensitive greedy grouping. `--step-judge cluster` chooses the earliest largest cluster; `--step-judge model` invokes one more structured model call only on a tie, and falls back to the earliest cluster on judge errors. Only the selected action is eligible to execute: multi-action batching is disabled when K > 1. Sampling and judge tokens contribute to step usage; batch wall time includes sampling and judging. The vLLM `n=K` choice response counts its aggregate usage once.

**Safety:** every member of the winning cluster is inspected for approval risk using the observed accessibility tree, including semantic elements under pixel targets and scaling from the model's native frame. When the selected action needs approval, the normal computer executor requests it and runs its existing safety checks. When a different cluster member needs approval but the selected action does not, the step fails closed with an explicit user question and **no computer action**: the executor recomputes risk and cannot currently inherit the vote-cluster risk flag. This handoff costs another turn after user steering but prevents silently executing a lower-risk member of a mixed-risk cluster. The model tie judge can choose only an index; it cannot issue actions or override approvals.

`kai bench --backend <live> --oai-contract auto --rollouts N --judge narratives` (2–8) is bench-only. The normal app and `kai run` do not expose these flags. Each attempt re-runs the task's setup and teardown; a fresh browser lane uses a separate browser profile. **Run the whole bench in a disposable desktop or VM** (e.g. `scripts/desktop`) and set `KAI_BENCH_DISPOSABLE=1` explicitly. A `--browser --headless` profile alone is insufficient isolation: browser lane input can fall back to host desktop hands, downloads target the host, and external server-side mutations cannot be undone by closing a profile. Ensure task fixtures and external accounts are disposable, with resettable state between attempts. Rollouts require interactive approval and reject `--yes`; they also require recording and prohibit `--memory`, `--lessons`, `--procedures`, and `--repeat`, plus mock, replay and OpenAI-native backends. All N attempts are recorded individually. The bench writes `<task-id>-rollouts.json` into the batch run directory with a sanitized behavior narrative for each attempt and the winner. Programmatic task checks outrank model-described success; among equally verified attempts, a separate structured model judge selects a narrative. Invalid/unavailable judging picks the first tied attempt. The reported benchmark task is the selected attempt; all attempts remain saved. Narrative files omit typed text, model thoughts, targets, screenshots and raw errors; approval and execution-path values are restricted to fixed labels.

**Gemma-4 contract A/B (2026-10-16):** the two contract tasks in `bench/results/oai-contract-ab/gemini/gemma-4-26b-a4b-it/20261016T132320Z/` stopped at step 0 with an approval prompt despite `--yes` (baseline: 2/2; contract: 0/2). The contract model proposed `type` into mark 89 on contract-1 and a pixel `click` at (58,10) on contract-2. `TerminalApprover::approve` in `crates/kai-cli/src/console.rs` deliberately excludes every `Action::Computer` from auto-approval; without an interactive answer, it stops. This is an intentional safety gate, not evidence that best-of-K changed approval behavior (these were K=1 contract runs), and `--yes` cannot make contract GUI benchmarking unattended. For meaningful comparisons, run both sides in the same disposable environment with a person approving each computer action, or report the approval-induced stops separately rather than interpreting them as model accuracy failures. The `--yes` rollout validation rejects this misleading combination early; normal non-rollout contract runs retain their existing approval behavior.

## Tradeoffs and rejected approaches

Using spare bits in `Config.step_candidates` was rejected: `step_judge_model` is a dedicated bool, with the CLI's `StepJudge` enum distinguishing `cluster|model`. Sampling all backends through `n=K` was rejected because the OpenAI-compatible backends do not uniformly support it. Live trajectory rollouts on a normal desktop were rejected because they can repeat externally visible side effects. Selection does **not** replay the winning trajectory; only the measured selected outcome is reported.

## Verification and measurement

Unit tests cover overlapping and tied clusters, frame-proximate voting, winning-cluster approval inheritance, vLLM `n=K` request and response parsing, CLI validation and rollout selection/sanitization. Run focused `kai-core`/`kai-cli` tests and the CLI mock bench (without rollouts). For live A/B, compare K=1 to K=4 with two runs per side on the same task list and machine, separate `--out`/`--runs` directories, and report verified success, total input/output tokens, real model calls and p50 step latency. Rollouts use a disposable desktop, check-driven scoring and archived narratives. No accuracy improvement is claimed before these runs.
