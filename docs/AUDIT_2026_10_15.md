# Design and computer-use release audit — 2026-10-15

**Verdict: do not ship with full computer-use parity or cross-platform reliability claims yet.**

Original audited revision: `1bc97a65cbd18373ca1feceaf35ee646de89e5bd`.
The findings below record the research baseline. Implementation and current
validation are recorded in the remediation appendix; open gates remain explicit.

## Scope and evidence

Reviewed product promises against the GPUI app, engine, schema, native OpenAI
runner, desktop drivers, browser lane, model store/runtime, memory, packaging
and workflows. Inspected representative checked-in Home/Run, permissions,
approval, model and settings screen artifacts. These are staged Linux
screenshots, not live interaction evidence for this Mac or Windows.

Evidence levels below:

- **Reproduced:** exercised compiled Kai libraries locally with synthetic input.
- **Source-confirmed:** direct reachable code behavior; desktop reproduction pending.
- **Validation gap:** a supported configuration has no fresh evidence in this audit.

This audit does not establish that every screen or platform works. Interactive
UI navigation, Retina/mixed-DPI input, real Windows/Linux desktop runs and live
model accuracy remain unverified here. A passing unit suite does not close those gaps.

## Research baseline

Sources fetched on 2026-10-15:

1. [OpenAI computer-use API guide](https://developers.openai.com/api/docs/guides/tools-computer-use):
   recommends a persistent code-execution environment, with a structured computer
   tool as an alternative. The current structured protocol uses `computer`, ordered
   `actions`, and `computer_screenshot` output. Its action set includes move and drag.
2. [ChatGPT/Codex product computer use](https://learn.chatgpt.com/docs/computer-use):
   documents app access approvals separately from OS permissions. Windows uses the
   foreground desktop; macOS has additional background capabilities. Public docs
   do not establish the private implementation or a Rust-versus-Python speed ratio.
3. [Enigo 0.6.1 Mouse contract](https://docs.rs/enigo/0.6.1/enigo/trait.Mouse.html):
   ordinary scroll amounts are wheel notches whose distance depends on OS settings;
   pixel scrolling is a separate interface.
4. [Windows SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput):
   input injection is restricted by integrity level; a successful general input
   setup does not prove control of an elevated target.
5. [XDG RemoteDesktop portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html):
   native Wayland control has an explicit session/device-grant lifecycle, with
   EIS input and ScreenCast integration.

**Rust feasibility:** Kai already implements capture, accessibility, input,
HTTP inference and persistent browser sessions in Rust. Python is not required
for those operations. Equivalent model behavior requires matching action and
observation semantics, supported targets and evaluation, rather than translating
Python syntax. Existing Rust traits are a useful foundation. There is no current
like-for-like evidence that Kai is faster or more accurate than product Codex.

## Priority findings

P1 means resolve before broad release of the affected capability. P2 means a
material reliability or usability defect. P3 means documentation or maintenance
debt. IDs are intended to remain stable during remediation.

### A01 · P1 · Unicode text validation can panic — reproduced

`crates/kai-core/src/schema.rs`, `Decision::validate_and_clamp`, calls
`String::truncate(8192)`. A byte limit inside a UTF-8 character panics. An input
of 8,191 ASCII characters followed by `éé` reproduces it. Release uses
`panic = "abort"`, so this can terminate the process rather than reject a reply.

Acceptance: truncate at a valid character boundary while retaining a byte cap;
test boundary positions for two-, three- and four-byte characters through the
actual reply parser. Preserve the existing bounded-output behavior.

### A02 · P1 · Stop during inference still permits the returned action — reproduced

`crates/kai-core/src/engine/mod.rs`, `model_step`, awaits `decide`, then reaches
the actuator without checking the interrupt again. A fake model that trips the
interrupt before returning a click still produces **one click**, then the run
reports `Stopped`. The native runner has the same missing post-request check.

Acceptance: cancellation/revalidation before every side effect, including after
model calls and approvals. Test stop during inference, approval, typing, browser
startup and shell execution; no new mutation may start after cancellation is observed.

### A03 · P1 · “The model never sees the code” does not cover pixels — source-confirmed

`engine/observe.rs::look` redacts only `obs.grounding`. `perceive.rs::full`
encodes screenshot pixels with only Kai-window masking; `engine/record.rs` and
the app's `Sink` retain images. The browser screenshot path also provides pixels.
If an OTP or other typed sensitive value remains visibly rendered, a subsequent
full frame can disclose it to the model and saved history. Current human tests
use dummy JPEG bytes and therefore cannot detect this channel.

Acceptance: a synthetic page with a visibly rendered test code must produce
masked full images, crops, UI events and disk artifacts. Include error paths and
codes that are typed partially before an actuator error. Scope privacy copy to
the guarantee actually enforced.

### A04 · P1 · Approval hides part of the action being authorized — source-confirmed

`kai-app/src/approval.rs::fit_lines` cuts JSON lines to 48 characters;
`state.rs::describe` also cuts action text to 48. There is no full-action reveal.
Long shell commands, URLs and typed content can share a visible prefix but have
different consequences. The checked-in approval screenshot confirms the ellipsis.

Acceptance: display the exact executable action with selectable, scrollable text
and an explicit expansion option. Test two commands differing only after character
48 and a long multiline command. Keep controls reachable at 720×520.

### A05 · P1 · Native comparison runner implements a legacy protocol — source-confirmed

`kai-core/src/cua.rs` defaults to `computer-use-preview`, sends
`computer_use_preview`, reads singular `call["action"]`, and returns an
`input_image`. This does not implement the current protocol in source 1.
Changing only the model name cannot migrate it. No direct OpenAI key is present,
so current service compatibility was not tested. Legacy service availability is
not inferred from documentation absence.

Acceptance: separate versioned adapters; current request/response fixtures,
ordered action handling, response-status/refusal/error handling and a live smoke
test. Treat a no-call response as a result to inspect, not automatic task success.

### A06 · P1 · Move and drag are silently skipped — reproduced

`cua.rs::map_action` maps both to `Wait`. `schema.rs::Action` and the actuator
contract cannot express them. Native middle clicks also fall through to left
clicks. File dragging, selecting text, dragging sliders and hover menus therefore
do not have equivalent computer-use semantics.

Acceptance: implement explicit supported primitives with cleanup on cancellation;
otherwise return an explicit unsupported-capability result. Never record a skipped
mutation as successfully executed. Test a drag with an observable final position.

### A07 · P2 · Scroll units and targeting differ between lanes — reproduced/source-confirmed

`desktop.rs` uses wheel notches and, for an untargeted scroll, the existing cursor
position. `web/act.rs` uses 100 CSS pixels per amount and defaults to viewport
center. `cua.rs` divides pixel deltas by 100, rounds, clamps, and discards the
smaller axis. A `(150,250)` request becomes only three downward wheel units;
zero movement also becomes a nonzero scroll. Nested panels can consequently
scroll the wrong region or overshoot by different distances on each OS.

Acceptance: define wheel versus pixel units explicitly, retain both axes and zero
deltas, establish a deterministic target, and verify movement. Test nested panes,
horizontal/diagonal scrolling, touchpad-like deltas and each desktop's wheel settings.

### A08 · P2 · Nested UI scrolling consumes wheel events at an edge — source-confirmed

`vendor/ely-gpui-component/src/layout/scroll.rs` stops propagation whenever a
matching axis has any scroll range. It does not check whether the current offset
can move in the requested direction. An inner region at its end can retain wheel
events that should reach an outer scroll region. Live interaction reproduction is
still required. The dependency is excluded from workspace tests.

Acceptance: define intentional scroll chaining, test both ends of nested regions,
and verify mouse wheel and trackpad behavior. Record any vendor patch explicitly;
`vendor/README.md` currently describes the copy as unmodified.

### A09 · P2 · Running view does not adapt to the supported minimum width — source-confirmed

`main.rs` permits 720×520; `pages/sessions.rs` requests a 256 px sidebar;
`pages/running.rs` always creates a horizontal split. The remaining content width
is divided roughly in half, with no compact mode. The split's 280 px argument
constrains drag ratios, not an enforced minimum layout width; its cells clip
overflow. Text, controls and the frame become compressed below useful sizes.

Acceptance: switch to tabs/stacked content and a collapsible task list at a tested
breakpoint. Capture and interact at 720×520, 1024×768 and 1180×780 in both themes,
including long titles, approvals and large OS text settings.

### A10 · P2 · Transcript has no follow-newest or virtualization policy — source-confirmed

`pages/panes.rs::transcript` constructs every card on each render; `running.rs`
uses an ordinary ScrollArea without an owner scroll handle. There is no explicit
follow-newest, “new steps” affordance, or preservation policy when the user reads
older steps. The design document promises virtualized lists. History and other
library lists may differ; this finding concerns the run transcript and output blocks.

Acceptance: follow new work only when already at the end, retain manual reading
position, offer jump-to-latest, and measure a long transcript. Avoid rebuilding
all long terminal output for each incoming event.

### A11 · P2 · Primary-display capture limits multi-monitor operation — source-confirmed

`perceive.rs::primary` always chooses the primary display. A focused window on
another monitor is outside the capture and grounding. Separately,
`kill.rs::in_corner(-500,-500)` returns true: an entire negative-coordinate
monitor region can trigger the corner stop instead of just a small corner.

Acceptance: explicitly select the operating display/window, transform origins
and scale consistently, and bound the stop gesture to a real monitor corner.
Test left/above monitors, mixed scale factors, rotation and window moves.

### A12 · P2 · Default “success” is a model claim — reproduced

`Config::default` and settings disable outcomes/task checks; `gate.rs::claim_done`
returns Success when the ledger is not gated. An immediate mock `done` reports
Success for a task that performed no work. The app provides no independent
verifier. Existing tests exercise the opt-in gate, not a universal default guarantee.

Acceptance: distinguish “model reported complete” from “verified complete” in UI,
history, learned procedures and benchmarks. Evaluate stronger checks before
changing defaults; merely enabling a switch is not evidence of reliability.

### A13 · P2 · Capability badges can be green without exercising capability — source-confirmed

`permissions.rs::screen` checks monitor enumeration (and macOS preflight), not
actual capture. Windows accessibility is always Granted; non-Mac input reports
Granted unless the session says Wayland. This cannot detect capture failures,
blocked/elevated targets, or unavailable input. `all_granted` also accepts Limited.

Acceptance in the later permissions stage: distinguish granted, working, limited
and failed; test a harmless real operation; explain target-specific restrictions
and permission revocation. Keep Wayland limitations visible after onboarding.

### A14 · P2 · Platform support is narrower than one uniform experience — source-confirmed

Browser launch explicitly errors on Windows (`web/cdp.rs`); the Settings switch is
correctly disabled there. Native Wayland input is not implemented by Kai's own
session lifecycle, and the product documents XWayland-only control. macOS local
runtime distribution is Apple Silicon only. These are capability boundaries to
surface and test, not evidence that all OS paths are broken.

Acceptance: a capability matrix drives UI, CLI help, task routing and errors;
unsupported lanes cannot be selected through stale config. Define Windows browser
pipe support and native Wayland as separate milestones if required for release.

### A15 · P2 · Clipboard restoration covers text only — source-confirmed

`input.rs::paste` saves clipboard text, writes the task text, waits 250 ms and
restores only when a previous text value existed. Images/file clipboard formats
are not restored, and a user's clipboard update during the delay can be overwritten.
The doc comment promises restoration more broadly than implemented.

Acceptance: preserve supported formats and restore only if Kai still owns the
clipboard version. Test empty, image and text clipboards, slow readers and user
copy operations during paste. State limitations where the OS cannot preserve data.

### A16 · P2 · Delete-all-history leaves training records — source-confirmed

`pages/settings.rs` promises every saved run and screenshot is removed, but deletes
only `Settings::traces_dir()`. Opt-in training records are stored independently in
`Settings::runs_dir()` by `agent.rs`. They remain after this action.

Acceptance: explicit controls and descriptions for history, training records,
memory and cached procedures; test each directory with synthetic artifacts.
Avoid deleting active-run files while a writer is still running.

### A17 · P2 · More model files does not establish more model compatibility — source-confirmed

The catalog is extensible, but `models/hub.rs` accepts a single weights GGUF plus
a projector, and rejects split weights/gated repositories. Runtime support is
pinned. Entries do not specify an action dialect, image budget, coordinate format,
prompt template or verified compatibility with that runtime. All pulled models
use the same generic JSON harness and estimated memory fit.

Acceptance: separate installability, image support, valid actions and measured task
success. Add model profiles and a no-mutation image/schema test before marking a
model ready. Keep arbitrary pulls untested. Evaluate small-model profiles before
adding more catalog rows; do not imply native GUI training guarantees Kai's schema.

### A18 · P2 · Green workflows do not imply desktop acceptance — source-confirmed

CI is manually paused by owner policy. Windows/macOS recorded desktop runs use
`continue-on-error`; the macOS live check is also informational. Screenshot jobs
accept small/nonzero counts rather than all expected states. A workflow can be
green with missing screenshots or failed live control. This audit did not trigger
paid hosted workflows or change the owner's paused-CI preference.

Acceptance: a deliberate release gate checks required scenario outcomes, expected
capture filenames and nonblank content for the exact shipped artifact on each OS.
Keep exploratory benchmarks informational, separately from shipping criteria.

### A19 · P3 · A documented global launcher is unmounted — source-confirmed

`launcher_hotkey` is stored/defaulted but has no registration or consumer. The
shortcut list and DESIGN advertise a global Ctrl+Shift+Space launcher. This is a
dead setting and unsupported promise, not an orphan Rust module.

Acceptance: remove the promise/dead setting with compatibility handling, or build
and test the launcher in a separately scoped change. Do not reserve a nonworking key.

### A20 · P3 · Design and repository inventory have drifted — source-confirmed

README says nine shipped skills; validation finds ten. DESIGN starts with the old
saffron scheme, then adds the current Glass scheme, retains Windows/Linux-only
audience wording, and mixes intended components with implemented ones. Screenshots
cover staged data and do not prove keyboard/scroll/accessibility behavior. Three
owned Rust files exceed the 500-line repository rule: `agent.rs`, CLI `main.rs`,
and `tests/human_e2e.rs`.

Acceptance: one current screen/state specification with implementation status,
platform exceptions and acceptance evidence; archive superseded design prose.
Split oversized files by responsibility when their fixes are made.

## Open-model extension and speed criteria

Preserve `kai-core` ports, structured bounded decisions, accessibility grounding,
explicit risk gates and one desktop owner. Extend the action contract with typed
capabilities, units, supported buttons and cancellation semantics before expanding
the model shelf. Add runtime/model compatibility metadata and small-model-specific
image/context budgets. Keep execution policy outside model output.

Memory currently uses scope/word matching (`memory/recall.rs`), not embeddings.
Embeddings should be a later measured retrieval change; they do not address any
of the blockers above. Native app background operation is also broader than
browser CDP and must have its own concurrency/focus contract.

Measure equal tasks and outcome checks on equal hardware: success rate, retries,
model/observation/action latency, tokens, RAM, cancellation latency and p50/p95
task time, with repeated runs and variance. Separate harness overhead from model
inference. Current benchmark documentation does not establish Rust beating Python
or Kai beating product Codex.

## Remediation order

1. A01–A04: process survival, stop semantics, pixel privacy and inspectable approval.
2. A07–A11: define scrolling; verify nested UI regions, compact layouts and monitors.
3. A05–A06: modern protocol adapter and explicit move/drag/button capability support.
4. A12–A16/A18: truthful completion/privacy/capability UI and actual OS release gates.
5. A17/A19/A20: model profiles, dead setting cleanup and one current design document.

Before release, every P1 needs a failing-before/passing-after regression, every
supported desktop needs a real artifact acceptance run, and each product claim
must point to corresponding evidence. Permission scoping and embeddings can then
be designed with this capability contract in place.


## Foundation remediation — 2026-10-16

Implementation lives on `shashanks-Agent/computer-use-foundation`, based on
`0770053`. This is a first foundation milestone, not certification of Codex
product parity, frontier-model accuracy, or cross-platform release readiness.

### Implemented and exercised locally

- A01: Unicode byte caps preserve character boundaries (2/3/4-byte regressions).
- A02: cancellation races inference and approval waits. Shared execution carries
  cancellation/deadlines into queued input, native accessibility workers and
  launch callbacks. Browser held input has original-session release guards;
  unacknowledged cleanup poisons the lane. Failed native releases stop its queue.
- Desktop mutation ownership is shared across dispatchers and legacy input.
  Independent terminal jobs remain parallel; known Linux GUI shell launches
  acquire desktop ownership. Legacy approvals recheck grounding/foreground
  scope after acquiring ownership, before input.
- A03: code/secret entry latches before input, including ordinary secure-field
  passwords and partial failure. Subsequent pixel/crop egress stops for the run;
  known field values, events, prompts, output and trace records are sanitized.
  Raw model replies are discarded once the latch is active. This is suppression,
  not OCR-based pixel masking or a guarantee about secrets the harness never saw.
- A04: approvals display complete selectable JSON in a scroll area. This includes
  canonical payloads; CLI computer actions do not use automatic `--yes` approval.
- A05/A06: legacy-preview and current Responses actions normalize into the same
  engine/dispatcher used by opt-in local models. Current arrays and
  `computer_screenshot` outputs have scripted HTTP fixtures. Provider batches
  preflight all arguments/capabilities before input and stop after Skip, failure
  or an observed layout/image change. Provider final text asks for verification;
  it does not establish task success.
- A07: the versioned path preserves signed horizontal/vertical deltas and zero.
  Native execution advertises wheel notches; CDP advertises pixels. Unsupported
  units/buttons/actions fail explicitly. The historical mapping helper rejects
  pixel-to-notch approximation and unsupported move/drag instead of skipping.
- A19: removed the unused launcher setting and advertised global shortcut.
  Old saved settings containing the obsolete field still load and omit it on save.

The contract and dispatcher are in `crates/kai-core/src/computer/`. Native input
reuses Enigo/xcap/accessibility; browser input reuses CDP. No upstream sample code
was copied, no Python runtime or dependency installed, and no paid API call ran.
Upstream references and the reuse/license decision are in the approved spec.

### Rollout and remaining release gates

`computer_tools_v1` is off by default. CLI: `--computer-tools-v1`; app: the saved
setting of the same name. Native Responses current protocol also requires an
explicit compatible `--model`. The model catalog is intentionally unchanged.

Native Type requires a confirmed focused, enabled editable element; the model
must click/focus it and observe before typing. CDP's versioned capabilities are
currently Observe, Move, Scroll and Wait; click/type/key/drag stay unadvertised
until their full shared-contract browser acceptance passes. Legacy browser tools
remain available through the existing path with cancellation/release guards.

A08–A18 and A20 remain on the audit backlog unless specifically addressed above.
In particular: nested UI scrolling/minimum layouts, permissions UX, mixed-DPI
and multi-monitor desktop acceptance, clipboard fidelity, catalog profiles,
embeddings, history deletion and packaging require their own acceptance work.

Live approval-layout capture could not be validated: the capture helper selected
the foreground desktop instead of Kai. Those generated captures were deleted;
no valid screenshot is claimed. Host tests are synthetic/library/HTTP evidence.
Windows/Linux native runtime tests and cross-target clippy are unverified: only
`aarch64-apple-darwin` is installed. No target/toolchain downloads or hosted CI ran.
No speed or model-accuracy comparison with product Codex has been measured.
